01 — project
GET/overview

فكرة المشروع ⌄

لماذا FastAPI، ولماذا هذه الطرق الثلاث تحديداً.

الهدف: بناء ومقارنة ثلاث طرق مختلفة لجعل نموذج لغوي يجاوب بدقة عن أسئلة FastAPI التقنية — بدل استخدام مصدر بيانات جاهز، تم بناء الـ dataset من الصفر مباشرة من official FastAPI GitHub repository.

تم سحب ٨٥ صفحة توثيق رسمية (tutorial + advanced)، واستبدال كل إشارات الكود بالكود الفعلي من مجلد docs_src، وتنظيف المحتوى من HTML الزائد — لضمان أن كل طريقة تُختبر على معرفة حقيقية ودقيقة، لا نصوص مبتورة.

لماذا هذه المقارنة؟

لأن كل طريقة تمثل فلسفة مختلفة لحقن المعرفة داخل نموذج لغوي: الاعتماد على الذاكرة العامة، أو الاسترجاع اللحظي من مصدر خارجي، أو تطويع الأسلوب عبر أمثلة. المقارنة توضح متى تستحق كل طريقة استخدامها فعلياً.

QUESTIONWhat does response_model_exclude_unset do?
● PROMPT-BASED

إجابة طويلة ومفصّلة جداً — شرح كامل مع أمثلة كود متعددة (before/after)، ومقارنة مع response_model_exclude_defaults وresponse_model_exclude_none. غنية لكن أطول من اللازم لسؤال مباشر.

● RAG

"…omits default values from the result if they were not actually set explicitly. Only the values that were actually set will be returned." — إجابة مبنية حرفياً على صفحة Response Model من التوثيق الرسمي.

● FINE-TUNED

"…a parameter used to exclude fields that were not explicitly set… ensuring only fields provided by the user are returned." — جملة تعريفية واحدة مكثّفة، بنفس أسلوب الأمثلة الثلاثة المُعطاة له.

08 — takeaways
EVAL/findings

أهم ما تعلمته من المشروع ⌄

نقاط القوة الحقيقية اللي بنيتها، مو بس نتائج الأرقام.

01

بناء dataset من الصفر — لا استخدام مصدر جاهز، بل استخراج ٨٥ صفحة رسمية من GitHub مباشرة، مع دمج الكود الحقيقي بدل روابط placeholder.

02

نظام تصنيف أصيل بمحورين — مصدر المعرفة × درجة الخطورة، صُمم من الصفر ليكشف سبب فوز كل طريقة لا مجرد النتيجة.

03

مرونة هندسية حقيقية — التعامل مع 503/429 وتبديل النماذج بدل التوقف، بمعالجة أخطاء متدرجة (retry → model switch → quota check).

04

قرار منهجي واعٍ — اختيار Few-shot Prompting بدل المخاطرة بـ Cloud billing، وتوثيق السبب بصراحة كامل بدل التظاهر بأنه Fine-tuning كامل.

05

تقييم كمي لا انطباعي — استخدام LLM-as-a-judge على أربعة محاور + قياس Speed/Cost حقيقيين بالثانية والدولار، لا تقييم شخصي.

06

نتيجة غير متوقعة وموثّقة بصدق — RAG لم يتفوق كما هو متوقع نظرياً في Repo-Specific، وهذا وُثّق كما هو دون تحسين مصطنع للنتائج.
